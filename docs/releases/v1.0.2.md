> retail is a self-hosted mesh VPN. Your devices reach each other directly over WireGuard, from any network, through a server you run yourself: on one of your own devices or on a small VPS.

**A bug-fix release for 1.0.1.** On Windows, retail could stay off after **Update now**. Updates now show their progress, retail comes back on its own if a restart goes wrong, and the tray app can start it when it is off. When the server cannot be reached, the tray app says why, in your language. Devices that reach a server only through its internet tunnel now find it again when the tunnel's address changes.

> [!IMPORTANT]
> **Windows, updating from 1.0.0 or 1.0.1:** the restart after an update is done by the version you are leaving, so it can still fail this one time. If the tray says *retaild is not running* afterwards, quit the tray app (⚙ → Quit) and open retail again from the Start menu (the new tray app then shows **Start retaild**), run this installer once, or restart the computer. Running the installer is the surest way to update to 1.0.2.

## What's changed

### Updates

- **Progress.** Settings shows what an update is doing: downloading (*6.0 / 15.0 MB*), checking the download, putting the programs in place, then a bar while retail restarts, with the seconds so far.
- **Windows: retail comes back after an update.** Task Scheduler restarts nothing that exits with an error code, which an update's exit is. The restart is now started outside the task where Windows allows it, and the boot task also starts retail every minute when it is not running (and does nothing while it runs). A device updated to 1.0.2 puts the new boot task in place by itself.
- **Start retaild.** When retail is off, the tray's popup and Settings have a **Start retaild** button. It asks for administrator rights once and registers and starts the service again, which also repairs a broken boot registration.
- **A log file on Windows and macOS**: `C:\ProgramData\retail\retaild.log` and `/Library/Application Support/retail/retaild.log` (1 MB, then the previous one in `retaild.log.1`). Before, the service's messages went nowhere there.

### When the server cannot be reached

- **The tray app says why**, in the tray's language, under the device list: *No answer from the server* (the network may block it, or the server is off), *The server refused the connection* (is retail running there?), *The connection was cut on the way* (the network may block VPN connections), *Something answered in the server's place* (a filtering proxy or a Wi-Fi sign-in page), the server's name could not be looked up, no route, a proxy that wants a sign-in, or the server turning the device away. Joining from Settings explains a failure the same way. `retail status` prints the reason and the error itself.
- retail tells these apart by the kind of error, not its wording, and of all the ways it tried (IPv6, IPv4, proxies, tunnels) it reports the one that tells the most.
- **While the server is down,** devices connected through the relay show *Relay unavailable* instead of a working relay: the relay runs on the server. Direct connections keep working, and devices list the others as they were last seen. Everything reconnects on its own when the server is back.

### Settings

- **Joining is simpler.** The form asks for an invite code. It asks for an auth key only when you paste a server address (`https://…`) instead.
- **Check now** no longer turns the **Connect** button into *Connecting…*, and switching automatic updates on or off no longer shows *Saved.* under the connection card.

### Internet tunnel

- **A new tunnel address no longer strands devices that have a direct connection to the server's computer.** The server also gives devices its computer's retail address, and a device whose only way in was the old tunnel address reaches the server through the mesh and learns the new address there. Devices without such a connection (they restarted meanwhile, or only reach that computer through the relay) still need a new invite code, as before.
- The server's computer gives devices its retail address within seconds of starting, instead of half a minute later.

### Security

- **macOS: the programs moved to `/Library/retail/bin`**, a folder only root can change, with links in `/usr/local/bin` so `retail` still works in a terminal. On Intel Macs Homebrew makes `/usr/local/bin` the user's, so that user could replace the program launchd runs as root. An installed retail moves itself when it starts after the update. Until then, retail on macOS refuses to update itself in place while its folder can be changed by others: run the installer once.
- The helper node (`retaild --helper`) no longer writes its code to the log; `retail helper status` prints it (in Docker: `docker compose exec retail-server retail helper status`).

- The boot task's definition is written to retail's own folder, which only administrators can change, instead of the shared temporary folder, where another user could have replaced it before Task Scheduler read it.
- Stopping the service (`retaild service stop`, the installer, uninstalling) turns the boot task off until it is registered again, so it cannot start the old program in the middle of a reinstall.
- The Windows installer, which runs as administrator from wherever it was downloaded to, takes the Windows tools it runs (`reg`, `taskkill`, PowerShell) and the system DLLs it loads only from System32, never a file of the same name next to it in Downloads.
- Windows: the tray app and `retail` send their requests only to a retaild running as the system service or as the same user, not to a program another user managed to start in the services' session while retaild was restarting.
- Windows: if `C:\ProgramData\retail` is a link to another folder (made by another user before retail was installed), retaild replaces it with a folder of its own before writing anything.
- Linux: the installer's administrator step answers in a file the user made under an unguessable name, not in a fixed name in `/tmp`.
- The internet tunnel takes only a `….trycloudflare.com` address from cloudflared, and a single IPv6 network (/64) can hold at most 16 of the server's HTTP polling sessions.
- `install.sh` downloads over HTTPS only, redirects included.

## Upgrading

Installed devices update themselves within a few hours (or at once: tray app → ⚙ → Settings → **Check now**). Running the new installer over an installed retail updates it as well, and on Windows it is the surest way this time (see above). Server data, keys and settings stay.

Installing for the first time: see the [1.0.0 release notes](https://github.com/r2adkr/retail/releases/tag/v1.0.0) or the [README](https://github.com/r2adkr/retail#readme).

> [!NOTE]
> The installers are not code-signed yet. Windows SmartScreen asks to confirm: **More info → Run anyway**. macOS Gatekeeper wants **right-click → Open** the first time.

## Verify your download

`SHA256SUMS` lists every installer's checksum (also below).

```sh
grep retail-linux-x86_64.deb SHA256SUMS | sha256sum -c     # Linux: prints OK
grep retail-macos.dmg SHA256SUMS | shasum -a 256 -c          # macOS: prints OK
```

```powershell
(Get-FileHash .\retail-windows-x86_64.exe).Hash           # Windows: compare with SHA256SUMS
```
